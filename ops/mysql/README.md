# DB 마이그레이션과 실행 계정

앱 실행 계정은 현재 DB의 지정된 테이블에만 SELECT, INSERT, UPDATE, DELETE 권한을 갖는다. 마이그레이션 이력, 게시판 분류 이력, 이전 세션 교환 기한, 법적 문서 테이블은 SELECT만 허용한다. 전역 권한, DB 전체 와일드카드 권한, DDL, 임시 테이블, FILE, SUPER, GRANT OPTION은 허용하지 않는다. 앱은 기동 시 마이그레이션 버전과 실제 SHOW GRANTS 결과를 확인한다.

## 배포 순서

1. 기존 배포 방식의 로컬 DB 덤프 및 코드·환경 파일 백업을 검증한다. AWS 스냅샷을 추가하지 않는다.
2. 배포 후보 코드에서 `node backend/scripts/migrate.js --env <보호된 마이그레이션 환경 파일> --data-dir <운영 backend 경로>`를 실행한다. DB의 기존 사용자·게시글·정렬 순서·화면 설정·첨부 파일을 보존한다.
3. 사용자 생성 권한이 있는 별도 운영 계정으로 `node backend/scripts/provision-runtime-db.js --env <보호된 운영 환경 파일>`을 실행한다. 새 실행 계정 정보는 `WGS_RUNTIME_DB_USER`, `WGS_RUNTIME_DB_PASSWORD`, `WGS_RUNTIME_DB_HOST` 환경 변수로 전달한다. 비밀번호는 명령 인수·로그·Git에 남기지 않는다.
4. 앱의 DB 접속 설정만 새 실행 계정으로 바꾸고 기동한다. 이전의 마이그레이션 권한을 가진 접속 정보는 앱 외부의 접근 제한 파일에 보관한다.
5. 로그인, 관리자 승인·문제 수정, 게시판, 첨부, 학습, 학습노트와 세션 폐기를 확인한다. 다음 배포의 DB 백업과 스키마 변경은 앱 실행 계정 대신 별도 마이그레이션 계정을 사용한다.

`npm run migrate`와 `npm run db:provision-runtime`으로도 CLI를 실행할 수 있다. CSV 등 운영 데이터 가져오기는 별도 관리 작업이며 앱에 DDL 권한을 다시 주지 않는다.

## 보존과 실패 처리

- `--import-legacy-json`은 기본적으로 꺼져 있다. 이번 보안 배포에서는 사용하지 않는다. 오래된 JSON 파일로 현재 DB의 계정·화면 내용을 덮어쓰지 않는다.
- MySQL DDL 전체가 하나의 트랜잭션으로 취소되지는 않는다. 어느 단계든 실패하면 완료 버전을 기록하지 않고 앱 기동을 막는다. 원인을 수정한 뒤 같은 마이그레이션을 재실행할 수 있게 각 단계를 구성했다.
- 기존 실행 계정의 권한을 임의로 회수하거나 비밀번호를 바꾸지 않는다. 지정한 새 전용 계정만 생성·검증한다.
- 이전 버전은 기동 중 DDL을 수행하므로 롤백 시 이전 코드·의존성·환경 파일을 함께 복구한다. 새로 생긴 테이블과 기존 데이터·첨부는 삭제하지 않는다. HTTPS는 유지한다.

로컬 합성 DB에서 마이그레이션의 부분 실패·재실행·기존 값 보존, 실제 권한 거부, 제한 계정으로 전체 앱 동작을 검증했다. 운영 배포 검증은 별도 결과로 기록한다.
